## 2. Theoretical Concepts Researched

### 2.1 Tokenization & Token Economics
* **Tokens vs. Words:** LLMs do not read characters or words directly; they process chunks of text called **tokens** via Byte-Pair Encoding (BPE). As a general heuristic:
  $$1 \text{ token} \approx 4 \text{ characters} \approx 0.75 \text{ words in English}$$
* **Prompt (Input) Tokens:** All tokens passed inside the `messages` array (including System instructions, historical chat context, and the new user question).
* **Completion (Output) Tokens:** The tokens generated by the model in response.
* **Cost Asymmetry:** In modern LLM APIs, output generation requires sequential autoregressive decoding, making completion tokens roughly 3–4x more expensive than prompt tokens.
  $$\text{Total Cost} = \left(\frac{\text{Prompt Tokens}}{1,000,000} \times \text{Price}_{\text{in}}\right) + \left(\frac{\text{Completion Tokens}}{1,000,000} \times \text{Price}_{\text{out}}\right)$$

### 2.2 Model Hyperparameters & Sampling Mechanics
* **Temperature ($T$):** Controls the randomness of the model's token selection by scaling logits prior to the softmax function:
  $$P(w_i) = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$
  * **$T \to 0$ (e.g., 0.0):** Turns distribution into an argmax operation (greedy sampling). Outputs are deterministic, focused, and ideal for coding, data extraction, and classification.
  * **$T \approx 0.7$:** Balanced trade-off between logical consistency and vocabulary variety; ideal for conversational assistants.
  * **$T \ge 1.2$:** Flattens the probability curve, amplifying low-probability tokens for creative writing, brainstorming, and synthetic data generation.
* **Nucleus Sampling (`top_p`):** An alternative to temperature that restricts candidate tokens to the smallest set whose cumulative probability mass exceeds threshold $p$:
  $$\sum_{w \in V^{(p)}} P(w) \ge p$$
  * Setting `top_p = 0.1` restricts sampling to the top 10% probability mass, filtering out the "long tail" of unlikely words.
  * *Best Practice:* Adjust **either** `temperature` or `top_p`, not both simultaneously.
* **`max_tokens` & Finish Reasons:**
  * `finish_reason == "stop"`: Model naturally completed its thought or hit a stop sequence.
  * `finish_reason == "length"`: Generation was forcibly truncated mid-sentence because it exceeded the `max_tokens` budget.

### 2.3 Stateless Nature of LLMs & Conversation Memory
* **The Stateless Reality:** The API has no server-side memory. Each HTTP POST request is evaluated in complete isolation.
* **The Context Window Mechanism:** To simulate conversational memory, the client application must maintain an ordered list of message objects:
  ```python
  messages = [
      {"role": "system", "content": "..."},
      {"role": "user", "content": "..."},
      {"role": "assistant", "content": "..."}
  ]
  ```
* **Compounding Token Growth:** Every turn appends both the user query and the model reply. Consequently, prompt tokens grow linearly with conversation length, increasing per-turn inference costs and eventually approaching the model's maximum context window limit.

## 5. Key Debugging & Logic Insights

1. **The Streamlit `while True` Duplicate Widget Trap:**
   * *Problem:* Placing `st.text_input()` inside a `while True:` loop caused Streamlit to crash with `DuplicateWidgetID: There are multiple text_input elements with the same auto-generated ID`.
   * *Cause:* Streamlit is inherently event-driven and re-executes the entire script from top to bottom on user actions. A `while True` loop tries to render an infinite sequence of identical input widgets on a single web page.
   * *Solution:* Remove the `while` loop completely. Use `st.chat_input()` at the root level and persist state via `st.session_state`.

2. **The `base_url` Location Bug:**
   * *Problem:* Passing `base_url="https://api.groq.com/openai/v1"` inside `client.chat.completions.create()` caused `TypeError: Completions.create() got an unexpected keyword argument 'base_url'`.
   * *Cause:* `base_url` is a client-level transport configuration, not a request-level parameter.
   * *Solution:* Pass `base_url` during client instantiation: `OpenAI(base_url="...", api_key="...")`.

3. **History Desynchronization on API Failure:**
   * *Problem:* When an API call failed due to a rate limit or network timeout, the user's message had already been appended to `messages`. On subsequent requests, two consecutive `user` turns appeared without an intervening `assistant` response.
   * *Solution:* In the `except` block, perform defensive cleanup:
     ```python
     if messages and messages[-1]["role"] == "user":
         messages.pop()
     ```

4. **Parameter Typo Mismatches:**
   * *Problem:* Passing `temp=0.7` instead of `temperature=0.7` or `input="text"` instead of `messages=[{"role": "user", "content": "text"}]` triggered `TypeError: unexpected keyword argument`.
   * *Solution:* Adhere strictly to the OpenAI API specification schema for chat completions.
